# Danfoss Icon2 (Local)

*[English version](README.md)*

Кастомная интеграция для Home Assistant, управляющая термостатами тёплого
пола **Danfoss Icon2 RT** полностью по **локальному Tuya-протоколу** через
шлюз Danfoss Ally — без облака Danfoss и без интеграции
[`tuya_local`](https://github.com/make-all/tuya-local) (HACS).

Написана с нуля под конкретный дом: сырой маппинг датапоинтов (DP)
реверс-инжинирился вручную (см. [`docs/`](docs/)), потому что для
локального протокола этого никто раньше не публиковал — только для
облачного API Danfoss (см. [Благодарности](#благодарности)).

## Почему локально, а не через облако?

Очевидная альтернатива, [`mtrab/danfoss_ally`](https://github.com/mtrab/danfoss_ally),
работает хорошо, но зависит от доступности облака Danfoss. Эта интеграция
общается со шлюзом напрямую по локальной сети через
[`tinytuya`](https://github.com/jasonacox/tinytuya), поэтому отопление
продолжает управляться даже если пропал интернет или лежат серверы Danfoss.

## Что реализовано

- **`climate`** — по одной сущности термостата на каждый RT: пресеты
  Дома / Не дома / Пауза / Выходные, плюс ручной режим с прямым
  управлением температурой.
- **`sensor`** — температура пола, влажность, батарея, источник
  изменения уставки, статус адаптации.
- **`binary_sensor`** — термоголовка, неисправность, "изменено локально",
  статус замка от детей.
- **`number`** — верхний/нижний пределы температуры и уставки по каждому
  пресету (Дома/Не дома/Пауза/Выходные), редактируются напрямую.
- **`switch`** — включение преднагрева.
- **`lock`** — замок от детей (в отличие от облачной интеграции, здесь
  управляемый, не только для чтения).

Всё (адрес/учётные данные шлюза, device_id всех 6 RT) захардкожено под
конкретный дом в `credentials.py` — см. [Установку](#установка). Это
интеграция под один дом, не универсальная — формы настройки нет.

## Установка

> **Нужен `local_key` вашего шлюза?** Используйте
> [**get-key-danfoss-ally**](https://github.com/ivnlab/get-key-danfoss-ally) -
> он достаёт его (и таблицу `device_id`/`cid` всех RT) автоматически прямо
> из памяти приложения Danfoss Ally и печатает готовый сниппет. Нужен
> рутованный Android - подробности в его README.

1. Скопируй `custom_components/danfoss_local/` в `config/custom_components/`
   твоего Home Assistant.
2. Скопируй `credentials.example.py` в `credentials.py` (в той же папке)
   и впиши свои `local_key` шлюза, его device_id, IP в локальной сети, и
   `device_id`/`cid` каждого RT (см. блок выше). Как и почему это вообще
   работает — см.
   [`docs/LOCAL_KEY_EXTRACTION_METHOD.md`](docs/LOCAL_KEY_EXTRACTION_METHOD.md);
   как сопоставлялись номера датапоинтов — см.
   [`docs/RT1_DP_MAPPING.md`](docs/RT1_DP_MAPPING.md) (пригодится, если у
   твоего устройства DP отличаются).
3. Перезапусти Home Assistant.
4. Настройки → Устройства и сервисы → Добавить интеграцию → "Danfoss Icon2".

## Известные ограничения

- Уставка ручного режима (`manual_mode_fast`) и уставки именованных
  пресетов используют общий DP 114 как зеркало "текущей активной
  уставки"; запись в него срабатывает, только если режим (DP 2) уже
  переключён на Manual — иначе значение просто игнорируется (см. логику
  записи в `coordinator.py`/`climate.py`, разобрана путём живого
  тестирования).
- Датапоинт `switch_state` (нужен для полноценного статус-сенсора
  "преднагрев активен", как `pre_heating` у `danfoss_ally`) пока не
  найден — преднагрев пока доступен только как простой переключатель
  вкл/выкл (DP 1).

## Благодарности

`climate.py` и общий паттерн сущностей в `entity.py` адаптированы из
[`mtrab/danfoss_ally`](https://github.com/mtrab/danfoss_ally) (GPLv3),
которая управляет тем же железом через облачный API Danfoss. Слой
координатора/записи в этом проекте написан с нуля под локальный
Tuya-протокол — сырые номера DP, порядок записи для Manual-режима и все
прочие детали, специфичные для локального протокола, найдены независимо
(см. `docs/`), поскольку `mtrab/danfoss_ally` вообще не работает с сырыми
датапоинтами (использует именованные поля облачного API Danfoss).
